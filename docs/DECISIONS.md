# Decisions — image-service infra (Terraform)

Every "decide and document" item from the task list, with the reasoning.

## Compute platform: EC2 (Option A)

| Criterion | EC2 (chosen) | ECS | EKS |
|---|---|---|---|
| Cost | ~$15/mo (t3.small) + no control-plane fee | Fargate ~2× for two services, or an EC2-backed cluster to manage anyway | Managed control plane $73/mo + nodes |
| Effort | user_data + systemd, one file | task defs, services, capacity strategy | k8s manifests, IRSA setup |
| Learning | OS-level ops, Docker, systemd, IMDS/IAM roles | AWS-native orchestration | k8s |

For a single instance hosting two containers, ECS/EKS buy orchestration the
problem doesn't need yet. EC2 also teaches the credential chain end to end
(instance profile → SDK default chain → Secrets Manager), which was the point
of the exercise. Scale path when it's needed: same VPC, add an Auto Scaling
group + instance-level TG registration, or move backend to ECS.

## Terraform over the console

The full environment existed once as console work and was deleted. Rebuilding
it by hand would leave no artifact; Terraform gives a reproducible stack,
reviewable diffs, and a one-command teardown. State is remote (S3 +
DynamoDB lock table, created by `bootstrap/`).

## Networking

- **VPC `image`, 10.0.0.0/16**, two AZs: public (10.0.0.0/19, 10.0.32.0/19)
  and private (10.0.64.0/19, 10.0.96.0/19). App + RDS in private, ALB public.
- **NAT gateway: yes, single instance in AZ 1** + **S3 gateway endpoint**.
  ECR pulls and any general egress need a NAT; the S3 endpoint keeps
  image-object traffic off the NAT bill. A second NAT (per-AZ) is the
  production change, not a dev necessity.
- **Security groups**: ALB allows 80/443 from anywhere; app allows only
  3000/3001 from the ALB SG (+22 from inside the VPC); RDS allows 5432 only
  from the app SG. Chained least-privilege, no open egress anywhere it
  doesn't need it.

## RDS Postgres

- `db.t3.micro`, Postgres 16.8, 20 GB gp3 with autoscale to 100 GB, single-AZ,
  encrypted, 7-day backups. Dev-sized, prod-shaped.
- `image_admin` (not `postgres`/`admin`), password generated by Terraform,
  stored in **Secrets Manager** `image-service/dev/db-master` — never on the
  CLI, never plaintext.
- App-side connection string (DATABASE_URL), JWT secret and Lambda API key
  live in `image-service/dev/app`; only the EC2 instance profile (and
  Terraform) can read it.
- `rds.force_ssl=0` for dev because the Prisma connection string is not
  TLS-configured; flip to 1 and add `?sslmode=require` for prod.

## Compute (EC2)

- **t3.small** in private subnet AZ 1 (same AZ as the NAT gateway so its
  egress path has no cross-AZ hop).
- **Instance profile role** = the app's only AWS identity:
  S3 read/write on the image bucket, Secrets Manager read on the app secret,
  SSM (Session Manager — SSH not required), CloudWatch Logs for the
  containers. Docker pulls from ECR through the **amazon-ecr-credential
  helper**, which signs pulls with the same role — no login keys anywhere.
- **Reboot survival**: containers run with `--restart unless-stopped`, Docker
  is `systemctl enable`d, and a systemd unit (`image-service.service`)
  re-runs the start script at every boot, retrying the ECR pull for up to
  30 min (covers "instance booted before CI pushed the first image").
- **Migrations**: the backend Dockerfile CMD runs `npx prisma migrate
  deploy` before starting the API, so first boot applies the schema. Verify
  with `docker logs backend` (or the backend CloudWatch log group).
- **Logs**: containers use the `awslogs` driver → CloudWatch log groups
  `/image-service/backend` and `/image-service/frontend` (14-day retention).

## S3

- Bucket `image-service-images-<account>`, **new bucket for this environment**
  (the old manual test bucket was deleted with the rest of the manual setup;
  a fresh bucket keeps IAM scoping clean — instance role and Lambda role are
  scoped to this ARN only).
- **Fully private** (all Block Public Access knobs on, BucketOwnerEnforced,
  no public policy). Browsers only touch objects via presigned URLs the
  backend issues.
- **CORS**: PUT to `uploads/*` and GET/HEAD from the frontend's ALB origin —
  this is what makes browser presigned uploads work while the bucket stays
  private.
- **Key layout**: `uploads/<id>.<ext>` originals, `processed/<id>.jpg`
  Lambda output. The Lambda ignores anything outside `uploads/` (loop
  protection), and the backend only presigns into these prefixes.
- **Lifecycle**: incomplete multipart aborts after 7 days; originals tier to
  STANDARD_IA after 30 days. Original expiry is left OFF (`expire_uploads_days = null`)
  — dev can't silently delete user data; the compressed copy in
  `processed/` is what the gallery serves anyway.

## ALB & routing

- **Path-based routing** (no domain exists in dev, so subdomains and ACM
  aren't available yet):
  - `/auth`, `/images/*`, `/internal/*` → backend TG :3001 (matches the
    NestJS controllers 1:1)
  - `/*` → frontend TG :3000
  - Frontend pages (`/login`, `/records`, `/upload`) don't collide with the
    API paths, so the default-forward is safe.
- Health checks: frontend `/` (200), backend `/images` with matcher
  `200-499` (auth-protected routes answer 401 — an honest liveness signal
  until a dedicated `/healthz` exists).
- **HTTPS**: reserved — SG already allows 443; add an ACM cert (needs a
  domain) + a 443 listener, then switch `NEXT_PUBLIC_API_URL`,
  `CORS_ORIGIN`, and `BACKEND_URL` to `https://`.

## Image tagging scheme (Task 1.2)

- `:<sha>` — immutable, the tag CI deploys the Lambda with and the
  traceability anchor.
- `:latest` — rolling pointer (what the EC2 start script and the Lambda
  module reference until re-applied).
- Both pushed by the workflows; ECR keeps the last 10 images per repo
  (lifecycle policy) and scans on push.

## Lambda & S3 events

- Container image, `x86_64` (matches the linux/amd64 build), 512 MB / 60 s
  (sharp compresses typical photos in <5 s at that size).
- **Execution role**: `s3:GetObject` on `uploads/*`, `s3:PutObject` on
  `processed/*`, CloudWatch Logs. Nothing else — the Lambda never touches
  the database.
- Env: `BACKEND_URL` = ALB URL (`/internal/*` is path-routed to the API),
  `LAMBDA_API_KEY` from Terraform (generated + stored in Secrets Manager),
  `NOTIFY_MODE=api`, `TARGET_BUCKET` = the image bucket.
- **S3 notification**: `ObjectCreated:*` on prefix `uploads/` → function.
- **Image-based Lambda bootstrapping**: a `package_type=Image` function must
  reference an existing image. On the first apply (clean account, no CI run
  yet) the function is created with `create_lambda = false`; after the
  lambda workflow's first green run, set `create_lambda = true` and
  re-apply — that creates the function, its S3 permission, and the bucket
  notification.

## Credentials — the invariant (Tasks 1 & 2.7)

Static AWS access keys exist in exactly one place: the operator's local AWS
CLI profile (human access for running Terraform). Every **workload** uses
roles only:

| Workload | Identity | Gets |
|---|---|---|
| GitHub Actions | OIDC → `GitHubActionsWorkflowRole` | ECR push ×3, Lambda code update |
| App instance | instance profile role | S3 bucket RW, app secret read, SSM, logs |
| Containers | same role via SDK default chain / ecr-login helper | — |
| Lambda | execution role | `uploads/*` read, `processed/*` write, logs |

No access-key/secret-key pairs are stored in repo secrets, task definitions,
pod specs (n/a), Lambda config, env vars, or Secrets Manager entries.
Verified during end-to-end testing.
## Bring-up lessons (recorded 2026-09-07)

1. **GitHub OIDC `sub` format**: on this account the sub embeds the GitHub
   org id *and* the workflow run id —
   `repo:emanworkplace15-star@229943178/<repo>@<run-id>:ref:refs/heads/main`.
   A plain `repo:org/repo:ref:...` trust entry silently fails. The trust
   policy therefore uses four `StringLike` patterns per repo covering every
   plain/id-annotated combination (see `modules/iam-oidc/main.tf`).
2. **AMI filtering**: a bare `al2023*` wildcard also matches the
   ECS-optimized AMIs. Pin the kernel-6.1 standard image
   (`al2023-ami-2023.*-kernel-6.1-x86_64`).
3. **Free-tier RDS limits**: automated backup retention maxes at 1 day on
   `db.t3.micro` (7 exceeds the free allowance). Postgres minor version must
   be one AWS actually ships (16.15, not 16.8).
4. **Registry prefixing**: modules pass *bare* ECR repo names and template
   the registry on exactly once — passing full URIs and prefixing again
   produced `registry/registry/repo` pulls that fail with "no basic auth
   credentials".
5. **Instance role needs ECR pull**: the `amazon-ecr-credential-helper`
   authenticates docker pulls through the instance role, so the role needs
   `ecr:GetAuthorizationToken` + pull actions on the app repos — without
   them the helper returns no credential and docker reports the same
   "no basic auth credentials" as above.
